# Current application architecture

The root directory contains independent repositories. This application composes NaBTools (Bluetooth and TPMS parsing), NaCBORUIforLVGL (CBOR projects, generic pages/events and bindings), and NaWServer (HTTP/WS/SSE). There are no local library copies. Board adapters, credentials, garage policy and product UI belong here.

One application task polls BtEngine, copies committed settings, publishes DataRegistry values and runs LVGL. SDK Wi-Fi callbacks publish an atomic address. HTTP reads owned snapshots under a mutex and submits bounded commands; it never borrows mutable Bluetooth/LVGL state. A separate storage task handles the shared filesystem and commits; see [storage.md](storage.md).

NaBTools' ResearchModule observes all received reports. A second collector filters TomTom manufacturer candidates before its independent 32-row table, so surrounding phones cannot evict TomTom rows. Both preserve full raw/AD/radio/classification facts, with byte strings converted to hex at the app's JSON/DataRegistry boundary. Unknown advertising does not create device instances. A configured-admission module creates TomTom devices only for the persisted registry; typed readings update the corresponding known sensor. Sticker byte order is normalized at this boundary. Radio reports, parse success, admission and actual readings are separate diagnostic stages.

Last readings remain known indefinitely while running. Loss of radio contact does not invalidate measurements, zero them or change their colors. Seconds since the last delivered reading appear immediately to the right of temperature on both LCD and web. A sensor never received since boot remains unknown. Monotonic ages and current readings are RAM telemetry, separate from durable instrument/garage configuration.

`src/ui/project.json` is the complete UI project; `project.cbor` is generated with the canonical sibling codec. All product widgets, top status bar, lower menu, page navigation, research row selection, paging and bindings are CBOR declarations. C++ registers data/actions and publishes values. There are three receiver pages plus Settings for 800x480 and corresponding compact pages for 320x170, each wrapped in a CBOR shell. The TPMS page pages over active vehicle wheels, while research uses bounded windows and stable observation IDs. No repeater implementation is copied into the app. The UI source remains read-only in ROM, preserving the existing shared FS UI catalog.

The status bar uses DHCP IP and SNTP local time (Asia/Yekaterinburg, UTC+5); unsynchronized time is `--:--:--`. Offline operation does not require time sync or Wi-Fi. Small fonts include Latin and Cyrillic subsets; licenses are retained. The large pressure font is the stock LVGL font.

LCD7 uses two screen-sized RGB565 buffers with LVGL DIRECT rendering. Only dirty rectangles are redrawn; the board publishes a complete back buffer after the last flush area and waits for RGB completion/VSYNC before allowing reuse. LVGL owns the synchronization of dirty areas between its two buffers. The RGB adapter uses the same sixteen-line bounce buffers as the UI demo. Display diagnostics include actual refresh/area/pixel counters; internal heap capacity is reported separately from PSRAM. These changes are board-specific and do not change the CBOR layout or generic bindings.

TPMS labels and shell status fields explicitly use LVGL CLIP with fixed bounds, so changing digit counts cannot introduce automatic line breaks. The wheel title and note retain their explicit newlines. Research details keep wrapping for their scrolling text. The generator preserves this distinction when regenerating the CBOR project.

The site adapts TechnicalShell: four appearance themes, three padding densities, RU/EN, fixed header, independent scroll regions, one-row numeric tables, explicit details dialogs, and fixed operation indicators without automatic banners. The same navigation tree is used at every width. On narrow viewports it closes into a three-pixel edge strip, opens with the unframed hamburger or a right swipe, and closes with a left swipe, backdrop, Escape or page choice. No separate mobile section dropdown is used. Pages: TPMS and receiver tasks, TomTom, all BT, read-only FS browser, Garage and known instruments. A shared tire-shaped `tpms-sensor` web component supports drag/drop and explicit sensor-then-wheel selection; conventional selectors remain available. The registry is a read-only identity table with explicit discovery registration and removal. Sensor names and wheel positions are never edited in that registry.

The app's compiled TPMS driver catalog gates both configured Bluetooth admission and available transports/protocols using the same define. `tpms.cpp` owns bounded parsed discovery observations and per-search pressure baselines; HTTP only copies snapshots and queues search requests. A 0.10 bar cumulative change latches a search marker without inferring wheel position. Immutable system identity, protocol identity, RAM measurements and the vehicle's wheel relation are distinct. See [storage.md](storage.md) for version 1 to 2 migration and trusted discovery registration.

The first/default web route is Home (`/` or `/#home`). A single `renderVehicleDiagram` draws both the garage editor and the read-only home view, sharing the bounded vehicle block and `tpms-sensor` component. Home always uses the committed `settings.active` vehicle, never an unsaved garage draft. Pressure and packet age come from retained parsed TPMS observations; temperature and age are aligned below each tire. Both vehicle selectors use the existing persistent selection command. Home disables sensor selection and drag/touch assignment. The old numeric TPMS/task page retains its `/#tpms` deep link. An explicit valid hash still opens its requested page; an empty or invalid route opens Home.

NaWServer serves assets and JSON/CBOR state, WS snapshots/diagnostic echo and bounded SSE. Detailed research reports use `/api/research?scope=tom|bt&detail=<stable-id>`; summary requests omit `detail`. A large vehicle snapshot uses HTTP plus a WS refresh signal instead of overflowing a WS frame. HTTP settings commands return an operation ticket and publish changes only after persistence. The old Basic login applies to HTTP routes and SSE; WS still has the prior unauthenticated behavior and accepts no mutating configuration commands.

`/api/display` exposes bounded diagnostics of the actual CBOR runtime and can dispatch page-button events through its existing CBOR handlers in the UI task. Optional LCD7 capture is the full RGB565 framebuffer, chunked for inspection; it proves rendered memory, not physical LCD acceptance. This route is authenticated like the other HTTP diagnostics.

Wi-Fi uses the independently extractable `lib/NaWFstore` component. Its portable manager owns profiles, priority-based retry, runtime enable windows and SoftAP sessions through injected storage, radio and clock interfaces. ESP-IDF adapters implement the radio and a versioned two-slot configuration in the existing NVS partition, namespace `nawfstore`. The SDK uses RAM credential storage; profiles are persisted only by NaWFstore. An ignored application header supplies first-use defaults only when no configuration exists. An intentionally saved empty list is retained. No automatic erase or repartitioning is performed.

The application facade serializes console, authenticated HTTP and CBOR action commands in a bounded queue serviced by a dedicated owner task. Public snapshots omit passwords; AP session credentials are available explicitly through the local console and native setup display. The legacy FS Wi-Fi fields seed startup policy once; later changes to those fields remain application requests, while subsequent boots load NaWFstore's NVS policy. The firmware does not generate fake measurements or timed reboots. Firmware updates preserve NVS and the existing shared partition. Build profiles are application board choices, not evidence of hardware validation.

Radio policy is application-owned: BLE always scans; settings select interval/window and the ESP-IDF backend asynchronously reconfigures while preserving scan intent. Wi-Fi has a separate event-task owner, bounded enable/off requests, an optional deadline and startup policy. HTTP callbacks and LVGL actions only enqueue requests. Main journaling distinguishes requested and SDK-applied scan timing, Wi-Fi RF state and per-instrument received/delivered counts.

Native appearance reuses the UI repository common Appearance module and Windows role compiler/catalog, with product-specific neutral control strokes and a night variant compiled by tools/native-appearance.mjs. App resources retain stable style addresses; CBOR nodes attach shared roles instead of local colors. Saved palette changes replace role values in the serialized UI context, retaining cached pages and geometry. Five scheme buttons are CBOR actions/bindings; the application persists the selected ID. Lower navigation tabs clip their upper rounded corners at the menu boundary, retaining visible lower curves.

Native receiver rows use neutral panels with bottom separators. Control selection uses a two-pixel inset outline, preserving bounds and content positions. Pressure numerals and units are separate CBOR labels: only the numerals use the indicator role, which is red in Night; remaining roles use dimmer red tones over black. This product policy does not change the public demo palettes.
